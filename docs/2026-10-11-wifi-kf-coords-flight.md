# WiFi 연결·칼만 추정·좌표 모드·AUTO 비행 — 펌웨어 `-35`~`-40`

2026-10-11 작업이다. [기울기 출력·비행 준비](2026-10-10-tilt-output-tagcal-flight-prep.md)(`-30`~`-34`) 다음 단계로, 실제 비행에서 AUTO(CH6)일 때 태그에서 벗어나는 문제를 고쳤다. 보드에 올라간 버전은 `TAGVISION-20261011-40`다.

## 1. 요약

| 요구·문제 | 한 일 | 결과 |
|---|---|---|
| USB 없이 비행 중 영상·값을 보고 싶다 | 보드 WiFi(공유기 STA, 실패 시 자체 AP) + TCP 3333 통로, WiFi 펌웨어 업데이트(OTA) | 행사장 공유기로 Mac 인터넷 유지한 채 연결. OTA 약 2~4분 |
| 영상이 느리다 | 사진을 텍스트(hex) 대신 **이진 묶음**으로, 보드가 스스로 계속 보내는 `snap stream` | 영상 속도는 결국 **인식 속도**에 묶임(아래 ROI) |
| 인식이 느리다 | **ROI 인식**: 마지막 태그 주변만 잘라 인식 | 태그가 보일 때 한 번 약 136ms, 초당 5.4장 (이전 2~4장) |
| AUTO에서 태그를 지나치거나 옆으로 샌다 | 카메라만으로 속도를 추정하는 **칼만 필터**(`vel_src 2`) + 카메라 기울기 보정(`att_comp 1`) | 태그와 거리 중앙값 **30cm → 11.6cm** |
| 사진 전송이 병목이 될 수 있다 | **좌표 모드**: 프레임마다 태그 좌표 한 줄(`pos`, 약 130바이트)만 보냄. 영상은 옵션(`v` 키)으로 유지 | 좌표 초당 약 5줄 |
| 태그로 돌아가는 속도가 너무 느리다 | 속도 프로필 상향 | 최고 20cm/s, 감속 시작 50cm |
| 비행 중 보드가 재부팅됨 | 코어 덤프 해석 → 카메라 태스크의 ESP 로그가 PSRAM 잠금으로 패닉 | 로그 끔. 이후 재부팅 없음 |

## 2. 무선 연결

### 2.1 라디오 선택

WiFi와 BLE를 함께 켜면 내부 RAM 여유가 24바이트까지 떨어졌다. 그래서 기본은 **WiFi만** 켠다(`RADIO_DEFAULT 1`).

| 명령 | 뜻 |
|---|---|
| `radio` / `radio wifi\|ble\|both` | 켤 라디오 (NVS 저장, 재부팅) |
| `wifi` | 상태: `mode`(sta/ap/connecting/sta_lost), IP, 신호, 클라이언트, 버린 줄 수 |
| `wifi scan` | 주변 2.4GHz 목록 |
| `wifi sta <이름> <비밀번호>` | 공유기 저장(NVS에만 저장, 소스·문서·로그에 남기지 않음) 후 재부팅 |
| `wifi ap` | 저장 지우고 보드 자체 WiFi로 |
| `wifi lite on\|off` | TCP로 보내는 줄 솎기 (approach 2Hz, flow/tag/vision 1Hz, msp 0.5Hz) |

- STA로 20초 안에 붙지 못하면 보드 자체 WiFi(AP, 이름 = BLE 이름)로 바뀐다. 비행 중 끊기면 AP로 바꾸지 않고 다시 붙기를 기다린다.
- mDNS `tagboard-b8b4.local`, TCP 3333. 클라이언트는 하나뿐이다. 새로 붙으면 이전 연결을 닫는다(뷰어 두 개를 띄우면 서로 끊는다).
- 공유기 이름은 대소문자를 구분한다. 끊김 이유 201 = 그 이름의 공유기가 없음.
- Mac에서 `No route to host`가 나오면 터미널 앱의 **로컬 네트워크 권한**을 켜야 한다.
- 행사장 WiFi에서 보드 신호는 −74~−80dBm였다. 응답 시간은 40~850ms로 크게 흔들렸고, 처리량은 초당 6~20KB였다.

### 2.2 WiFi 펌웨어 업데이트

```bash
pio run -e xiao_esp32s3_ota -t upload    # platformio.ini 의 upload_port(보드 IP)
```

FC가 아밍돼 있으면 보드가 업데이트를 받지 않는다. FC 상태가 5초 이상 안 들어올 때만 예외로 받는다. 비행 중 재부팅을 막으려는 설계다.

## 3. 칼만 추정 (`src/tag_kf.h`, `vel_src 2`)

광류센서 품질(21~42)이 낮아 속도로 쓸 수 없었다. 카메라 위치를 미분하면 3~5fps·지연 0.3s에서 잡음이 커서 제어가 흔들렸다. 그래서 축마다 3상태 칼만 필터를 둔다. PX4 Vision Target Estimator, ArduPilot AC_PrecLand와 같은 구조다.

- 상태: `e` 태그 상대 위치, `v` 기체 속도, `b` 모르는 가속도(바람·트림)
- 입력: FC가 측정한 자세(10Hz)로 낸 가속도 `g·tan(θ)`
- 측정: 사진을 찍은 시각 기준 지연 `L = 지금 − 촬영 시각 + 40ms`를 모델에 넣는다. `H = [1, L, −½L²]`
- 태그가 안 보이면 최대 3초(`kf_lost_ms`)까지 예측으로 태그 쪽으로 간다. 이때 속도는 12cm/s 이하다.
- 제어는 0.5초 뒤(`kf_pred_s`)의 예측 상태로 한다. 명령 → 실제 자세 지연이 약 0.6초라서다.
- 다시 시작할 때는 기억한 바이어스 `b`를 쓰고, `b`는 가속도 명령에서 미리 뺀다.

| 파라미터 | 기본 | 뜻 |
|---|---|---|
| `vel_src` | 2 | 0 광류, 1 카메라 미분, 2 칼만 |
| `kf_att_input` | 1 | FC 실측 자세를 가속도 입력으로 |
| `kf_pred_s` | 0.5 | 제어에 쓰는 예측 시간 |
| `kf_lost_ms` | 3000 | 태그 없이 예측으로 가는 최대 시간 |
| `att_comp` | 1 | 촬영 시각의 기체 기울기로 카메라 위치 보정 (`h·tan(θ)`) |

## 4. 인식 속도 — ROI

VGA 전체 화면 인식에 걸리는 시간은 축소 배율(dec)에 따라 다음과 같았다. dec 2: 540ms, 3: 255ms, 4: 160ms, 6: 40~80ms.

마지막 태그 둘레만 잘라서 인식한다. 자르는 반폭은 `max(90px, 2.5 × 한 변)`이다. 축소 배율은 `한 변/배율 ≥ 24px`를 지키는 가장 큰 값을 쓴다. 태그를 놓치면 전체 화면으로 돌아간다. 잘라낸 좌표와 호모그래피는 원래 화면 좌표로 되돌려 쓴다.

## 5. 좌표 모드·뷰어 (`tools/cam_view.py`)

```bash
uv run --with pyserial --with pillow python3 tools/cam_view.py --wifi 192.168.0.151 --mode coords \
    --init "approach flight;exp fast" --ap-log flight.jsonl
```

- `--mode coords`(기본): 보드에 `snap stream off`를 보내고 `pos` 줄로 레이더 화면을 그린다. 태그 상자·3초 궤적·칼만 위치(하늘색)가 나오고, 예측 중이면 주황으로 표시된다.
- `--mode video`: `snap stream <ms>`로 보드가 이진 사진을 계속 보낸다.
- 키:
  - `v`: 좌표/영상 전환
  - `p`: 사진 한 장
  - `o` / `w`: 접근 켜기 / 그림자 모드
  - `q`: 종료
- `pos` 줄: `{"type":"pos","id","cx","cy","s","rot","r","f","ke":[R,F],"kp","roi","dms"}`. 태그가 없으면 `id −1`과 칼만 값만 보낸다.

## 6. 보드 재부팅(패닉) 원인

코어 덤프는 `esp-coredump`가 ELF 해시 불일치로 거부했다. 그래서 코어 ELF를 뽑아 xtensa gdb로 직접 열었다.

- 원인: 카메라 태스크의 `ESP_LOGE("FB-SIZE")`가 처음 쓰일 때 newlib 콘솔 잠금이 **PSRAM에 할당**되어, 스핀락에서 패닉이 났다.
- 수정: `esp_log_level_set("*", ESP_LOG_NONE)`, 부팅 직후 `printf`/`fflush`로 잠금을 내부 RAM에 미리 만든다.
- 출력 버퍼는 PSRAM으로 옮겼다. `-40` 기준 RAM 최소 여유는 약 18KB다.

## 7. FC 모드 범위를 FC에서 읽기

`MSP_MODE_RANGES`(34)에서 MSP RC override(박스 50)의 채널·범위를 읽어 AUTO 판단에 쓴다. 지금 FC 설정은 CH6 900~1300(끝 미포함)이다. `msp` 줄의 `ovr_ch`, `ovr_us`, `ovr_src`(`fc`/`config`)로 확인한다.

## 8. 비행 결과 (`-40`, 실내, 태그 1장, 높이 1.0~1.3m)

AUTO 약 90초, 스로틀은 조종기:

| 항목 | 이전 (`-34`대) | `-40` |
|---|---|---|
| 태그와 거리 | 중앙값 약 30cm | 중앙값 **11.6cm**, 90% 22cm, 최대 35cm |
| 태그 인식 | 자주 놓침 | 148회 중 147회 보임 |
| 바이어스 `b` (좌우) | +46cm/s²까지 증가 | +14cm/s² 이내 |
| 인식 | 초당 2~4장 | 초당 5.4장, 136ms (ROI 68/69회) |
| 오류·과속 | — | 없음. MSP 오류 0, 송신 50Hz / 응답 49Hz |

- 남은 흔들림: 좌우는 약 11초 주기로 ±11cm, 앞뒤는 약 4.5초 주기로 ±8cm다.
- 좌우 축이 뒤집혔다면 태그에서 점점 멀어졌을 것이다. 35cm 안에서 계속 돌아오므로 축 방향 문제는 아닌 것으로 본다.
- 배터리는 12.11V에서 11.37V로 내려갔다(7.9A).
